1. **缺少数据架构师**
   - 影响：Entity、Domain 设计可能错误，后续大规模返工
   - 缓解：外部咨询 或 P1 先学习，P2 再请专家

   - 影响：MCP Server、API 集成受影响
   - 缓解：保持兼容层 + 完整回归测试

3. **团队学习曲线陡峭**
   - 影响：实施周期延长 50-100%
   - 缓解：从简单场景开始 + 培训

### 🟡 中风险（需要监控）

4. **LLM 能力不足以理解复杂语义**
   - 缓解：Trusted Assets 降低对 LLM 依赖

5. **Policy Engine 性能瓶颈**
   - 缓解：提前性能测试 + 缓存优化

## 💡 常见问题（FAQ）

### Q1: 为什么当前覆盖度评估是 25-30%，而不是更高？

**A:** 虽然 RDS Agent 有基础的 Schema、Metric、Dimension 配置，但缺少 Genie 的核心能力：
- ❌ Entity 和语义图（防止错误聚合）
- ❌ Measure/Metric 分离（口径统一）
- ❌ Domain（多场景支持）
- ❌ Policy Engine（企业级安全）
- ❌ Trusted Assets（关键指标锁定）

这些是语义层的"灵魂"，没有它们就无法保证数据分析的正确性和一致性。

---

### Q2: 为什么需要 12 周？能不能更快？

**A:** 可以选择 MVP+ 路径（6 周），但只能达到 55% 覆盖度。

标准路径（12 周）包含：
- P1（3 周）：基础语义对象
- P2（8 周）：Entity、Policy、Trusted Assets、时间智能
- 集成测试（1 周）

如果跳过 P2，会导致：
- 仍然无法防止聚合错误
- 仍然无法企业级部署（缺少权限治理）
- 关键指标仍然不可信

---

### Q3: 必须要数据架构师吗？

**A:** 
- **P1 阶段**：不是必须（可以团队学习）
- **P2 阶段**：强烈建议（Entity、Domain 设计需要专业能力）

如果没有数据架构师，可以：
1. 外部咨询（2-3 次 workshop，约 ¥5-10 万）
2. 团队培训 + 从简单场景开始
3. 参考 Cube.js、dbt 的开源实践

但风险是：Entity 设计错误会导致后续大规模返工。

---

### Q4: 会不会配置太复杂，难以维护？

**A:** 这是合理的担忧。缓解措施：

1. **提供配置工具**（Week 12-14 的 P3）
   - YAML 校验工具
   - 配置生成器
   - 可视化编辑器（可选）

2. **渐进式迁移**
   - 先迁移 1-2 个核心场景
   - 验证后再推广

3. **培训和文档**
   - 配置最佳实践
   - 常见模式库

实际上，结构化配置比 Prompt Engineering 更容易维护和审计。

---

### Q5: 对现有集成（MCP Server）有什么影响？

**A:** 
**外部接口不变：** `query_data(question)` 保持兼容

**内部增强：**
- 更准确的意图理解（有 Domain、Entity）
- 更安全的查询（有 Policy Engine）
- 更可信的结果（有 Trusted Assets）

**迁移策略：**
- 保持兼容层
- 新旧配置并存过渡期
- 完整回归测试
