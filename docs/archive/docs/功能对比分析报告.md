# RDS Agent vs Genie 语义层功能对比分析报告
## 基于当前 YAML 配置的详细功能评估

---

## 一、执行摘要

本报告对比 Databricks Genie 语义层设计与 RDS Agent 当前实现，基于实际的 YAML 配置文件进行深入分析，明确哪些功能已实现、哪些缺失、哪些需要增强。

### 关键发现

**✅ 已实现的核心功能（40%）：**
- 基础 Schema 定义（表、字段、类型）
- 简单指标定义（6个预定义指标）
- 基础维度映射（5个维度）
- 业务术语同义词（12组术语）
- 基础 Join 关系（4条 Join）

**⚠️ 部分实现但需增强（30%）：**
- Metric 定义（未区分 Measure 和 Metric）
- Relationship（缺少基数控制和路径优先级）
- Filter（分散在 metrics 中，未对象化）
- 时间处理（基础支持，无同比环比）

**❌ 完全缺失的关键功能（30%）：**
- Domain（业务领域）
- Entity（业务实体）和语义图
- Trusted Assets（认证资产）
- Policy Engine（权限治理）
- Benchmark 体系（评价系统）
- 语义对象生命周期管理

## 五、关键差距总结

### 🔴 最关键的 5 个缺失功能（阻塞性）

1. **Entity 和语义图** - 无法防止错误聚合，这是语义层的根基
2. **Measure/Metric 分离** - 导致指标口径混乱，无法支持复合指标
3. **Domain** - 无法支持多业务场景，限制了产品适用范围
4. **Policy Engine** - 无法企业级部署，安全风险极高
5. **Trusted Assets** - 关键指标无法锁定，财务、董事会 KPI 不可信

### 🟡 重要但非阻塞的缺失功能

6. **Benchmark 体系** - 影响长期质量保障
7. **Filter 对象化** - 影响配置维护效率
8. **时间智能** - 影响常见时间分析需求
9. **Relationship 增强** - 影响复杂 Join 场景
10. **语义检索增强** - 影响匹配准确率

### 🟢 可以暂缓的功能

11. **多币种/多语言** - 对单一市场影响较小
12. **维度层级** - 钻取分析可通过多次查询实现
13. **双层语义** - 单 Agent 场景不需要
14. **高级 Metric 类型** - 可通过 SQL 手动实现

## 七、实施建议

### 立即行动（Week 1-2）

1. **创建 domains.yaml**
   - 先定义一个 `retail_sales` Domain
   - 迁移现有配置到该 Domain

2. **增强 schema.yaml**
   - 为每个表添加 `grain` 字段
   - 为每个表添加 `entities` 定义
   - 为每个 Join 添加 `name`、`join_type`、`auto_join`、`priority`

3. **拆分 metrics.yaml**
   - 创建 `measures.yaml`，迁移原子度量
   - 重构 `metrics.yaml`，改为复合指标定义

4. **创建 filters.yaml**
   - 提取 metrics 中重复的 filters
   - 定义为独立的 Filter 对象

### 短期实施（Week 3-6）

5. **创建 policies.yaml**
   - 定义表级权限
   - 定义行级权限（RLS）
   - 定义列级脱敏

6. **创建 trusted_assets.yaml**
   - 识别 3-5 个关键指标
   - 定义认证查询模板

7. **创建 benchmarks.yaml**
   - 从 examples.yaml 迁移并增强
   - 添加期望意图、SQL 要素、结果

### 中期优化（Week 7-12）

8. **增强 dimensions.yaml**
   - 添加时间维度的粒度、偏移、窗口

9. **增强 terms.yaml**
   - 添加 `maps_to` 字段
   - 添加 `exclusions` 字段
   - 添加 `context` 字段

10. **建立配置治理流程**
    - 添加 `status`、`version`、`owner` 字段
    - 建立配置审批工作流

## 结论

RDS Agent 目前具备了 **25-30% 的 Genie 语义层能力**，基础扎实但距离企业级语义层还有较大差距。

**最关键的 3 个缺失：**
1. ❌ **Entity 和语义图** - 防止错误聚合的根基
2. ❌ **Measure/Metric 分离** - 指标口径统一的前提
3. ❌ **Domain + Policy** - 多场景支持和安全治理

**建议优先实施顺序：**
1. Domain + Entity（2 周）→ 建立语义基础
2. Measure/Metric 分离（1 周）→ 口径统一
3. Filter 对象化（3 天）→ 配置复用
4. Policy Engine（2 周）→ 安全治理
5. Trusted Assets（1 周）→ 关键指标锁定
6. Benchmark 体系（1 周）→ 质量保障

通过 **8-10 周的分阶段实施**，可以将覆盖度提升到 **75-80%**，达到企业级语义层的基本要求。
